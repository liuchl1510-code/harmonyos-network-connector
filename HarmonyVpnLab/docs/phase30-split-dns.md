# 0.24.0：可选白名单 DNS 分流与对照验证

2026-09-23，版本 **0.24.0/code45**。新增默认关闭的“白名单 DNS 分流”，保留原来全部经节点查询的默认行为。ARM64 C2 调试包已构建核验并安装；同一台鸿蒙电脑上的正式对照、手动重连、界面与设置恢复检查已完成。单台设备的小样本结果不构成普遍提速结论。

## 使用与查询去向

断开连接并等待清理完成后，打开首页“网络设置”，选择“白名单（绕过大陆）”，在 DNS 区选择“白名单 DNS 分流”并保存。设置在下次连接时生效。选择“全部经节点（默认）”可恢复原查询方式。

DNS 分流只按已知域名类别选择解析器，保留如下顺序：

| 域名类别 | DoH 路径 |
| --- | --- |
| `geosite:google` | 优先经当前节点，覆盖较宽泛的大陆类别匹配 |
| `geosite:private`、`geosite:cn` 及 `alidns.com`、`doh.pub`、`dot.pub`、`360.cn`、`onedns.net` 的域名及子域 | 通过当前物理网络访问直连 DoH |
| 其他域名 | 经当前节点访问代理 DoH |

代理 DoH 沿用原 `dnsUrl`，默认 Cloudflare `https://1.1.1.1/dns-query`；其 URL 中的域名仍交给节点解析。新增直连 DoH 默认阿里公共 DNS `https://223.5.5.5/dns-query`，可在设置中修改。直连提供方可见查询的域名和当前物理网络出口，默认关闭的目的也是保留用户既有查询去向。

直连 URL 初期只接受 HTTPS IPv4 字面地址及路径，拒绝本机回环、非单播范围及 VPN 自身的虚拟地址，避免递归查询解析器自身或形成虚拟接口循环。允许单播局域网地址，但 TLS 仍须正常验证；公共 DoH 不保证解析局域网私有域名。没有把节点服务器的连接前域名解析改为分流 DoH。

未命中域名类别、仅按 IP 规则直连的业务连接，其 DNS 不一定直接查询。查询失败不会自动改用另一条 DNS 路径。IPv6 继续捕获后阻断；A 查询保持 IPv4，AAAA 和非 IP 类型保留原处理。节点检测继续使用独立的默认全部代理配置，不采用日常 DNS 分流和应用选择列表。

## 设置保留与实现

- 新网络策略为 schema 3，增加 `dnsMode`（`proxy`／`split`）和 `directDnsUrl`。schema 1／2 严格校验后只在内存迁移，默认补为 `proxy`；不因读取重写旧文件，显式保存才原子写回。
- 全局或自定义规则模式下，分流偏好及直连 URL 保留但不生效。非默认直连 URL 即使切回 `proxy` 也保留显示，因此非法输入不会藏在无法修改的字段中；保存仍检查完整策略。
- 连接启动后冻结完整策略。网络恢复继续使用当前会话的 DNS 模式与地址，不采用外部修改的新偏好；下一次新连接才读取新设置。
- Xray 配置使用独立的 `dns-via-node`／`dns-via-direct` 标签及前置路由。匹配的查询以 `finalQuery` 终止后续候选，关闭跨解析器回退及并行查询，保留系统 hosts 禁用和原 DNS／IPv6／虚拟接口保护。
- 沿用既有固定版本 Xray 26.6.1、GeoData 和 Socket 保护路径；没有修改 C++、Go 适配或上游核心源码。新增能力来自 ArkTS 配置、设置界面及对应验证。

## 鸿蒙电脑正式对照

同一台 API26／ARM64 鸿蒙电脑上完成 3 轮、18 个独立连接试验，交替比较原代理 DNS 与新分流 DNS。共 30 项 DNS／HTTPS 测量全部成功，18 次连接均有正常清理证据；18 项显式 DNS 查询均在各自测量时间窗内命中预期解析器。每种目标、每种模式各 3 次。DNS 组三种域名轮换次序；两个 HTTPS 目标分别在新核心中发起完整 GET。第 14 次连接前曾因应用失去前台中断，前 13 次结果保留并核对，恢复后完成余下试验，没有把试运行样本混入正式结果。

下表单位为毫秒，括号内为最小值～最大值。这里的“首次”指该试验中首次主动查询该域名；系统其他应用可能已预热同一个 DoH 连接池。第二次查询可能命中缓存。

| 显式 DNS A 查询 | 全部经节点：首次中位数（范围） | 分流：首次中位数（范围） | 第二次中位数：原／新 |
| --- | ---: | ---: | ---: |
| 百度 | 182（170～458） | 17（14～27） | 6／8 |
| Google | 174（171～183） | 673（641～678） | 8／6 |
| Cloudflare | 176（173～180） | 671（645～686） | 6／12 |

| 完整 HTTPS GET | 全部经节点：中位数（范围） | 分流：中位数（范围） | SDK 报告的 DNS 阶段中位数：原／新 |
| --- | ---: | ---: | ---: |
| 百度 | 2005（1726～3696） | 174（172～207） | 590／12.79 |
| Cloudflare | 906（888～1946） | 1424（1368～1440） | 165.36／676.32 |

12 次 HTTPS 请求均报告新建连接、HTTP 200，响应体通过限定校验。SDK 的 `dnsTiming` 是该请求的阶段耗时，不是节点 RTT；完整 GET 则还包含 TLS、服务器响应和下载。百度的改善同时改变了 DNS 提供方、网络路径以及可能返回的 CDN 地址，无法单独归因于某一个因素。原模式共用一个代理 DoH 连接池；新模式的 Google 例外与其余代理域名各有独立池。其他应用的查询可能提前预热原模式的连接池，因此表中 Google／Cloudflare 的较慢首次测量也不能解释为每次固定增加约 500 毫秒。系统、上游解析器缓存和其他应用负载未重置；每组 3 次不足以得出统计显著性或全站提速结论。新选项仍默认关闭。

本地完整计划、逐项回执、脱敏汇总和路径核对分别保存在 `build/phase30-pc/matrix-plan.json`、`matrix-progress.json`、`benchmark-summary.json`、`dns-path-audit.json`；私有节点和原始日志只留本地。此前 0.23.0 的[电脑稳定性记录](phase29-pc-stability.md)属于旧 DNS 配置，不替代本轮验证。

## 补充验证与收尾

保存分流设置后，通过应用“重新连接”在同一会话内完成一次重连，恢复次数增加 1；随后百度、Google 的 DNS 查询及百度、Cloudflare 的完整 HTTPS 请求均成功。新产生的核心日志仍显示百度使用直连 DoH、Google 使用代理 DoH。该测试验证了手动重连，不能替代 WLAN 断开后自动恢复的单独试验。

网络设置页在常规电脑窗口与 600 vp 窄窗口、双倍字号下，DNS 模式、两个地址输入和保存按钮等 6 个控件均可找到并操作；调试日志确认窗口与字号设置实际生效。窗口恢复到本轮开始时的位置与尺寸，偏差不超过 2 像素。这里核对的是本应用的无障碍控件位置和可操作性，没有进行像素截图评估。

回到原有“全部代理”与默认代理 DoH 后，一次新的连接完成 DNS／HTTPS 检查并正常清理。最终独立读回确认 VPN 已断开、服务进程不存在，恢复前后节点库、当前节点、延迟记录、外观等 6 份用户文件按字节一致；网络策略与本轮恢复测试前保存的 schema 3 文件按字节一致。更早的 schema 2 策略原有字段未变，显式保存后版本为 schema 3，DNS 模式为默认 `proxy`。

真机的“直连 DoH 返回 404”故障注入**没有完成**：鸿蒙电脑的输入面板夺取了调试焦点，自动文本输入未修改地址。测试在发起新连接前停止，没有留下错误 DNS 地址。固定 Xray 核心的 42 个离线场景覆盖 `finalQuery` 和失败不跨路径的负向对照，但这不等同于真实设备上的服务提供方故障试验。后续若继续扩展此模式，还需单独验证真实解析器故障、系统断网恢复及更多网络环境。

API24 平板仍按此前要求暂停。个人节点、设备标识、原始核心日志、未脱敏窗口树、签名材料及调试 HAP 不进入公开仓库。
