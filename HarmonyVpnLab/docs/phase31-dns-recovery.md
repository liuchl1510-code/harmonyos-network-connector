# 0.25.0：DNS 故障分类与鸿蒙手机恢复验证

2026-09-26，版本 **0.25.0/code46**。本轮完善分流 DNS 的日常检查，并提供不修改用户偏好的受控故障入口；测试目标为一台 API26／ARM64 鸿蒙手机及此前已验证的一条节点。ARM64 C1 已构建、核验及覆盖安装。正常分流、真实 HTTP 404、核心极短超时、同会话断网恢复、离线等待时主动断开及日常模式复验均已核对，最终 VPN 已断开。验收范围按下面的具体场景限定。

## 日常检查的变化

普通连接仍使用已有网络设置，白名单 DNS 分流保持默认关闭。启用分流的会话在首页点击“检查连接”时，执行以下固定目标：

| 检查 | 目标与条件 | 结果含义 |
| --- | --- | --- |
| 直连 DNS | 固定 `www.baidu.com` 的 A 查询，仅在服务当前有效策略为白名单分流时执行 | 检查这次直连类别的解析；失败不认定代理节点失败 |
| 经节点 DNS | 固定 `www.cloudflare.com` 的 A 与 AAAA 策略查询 | A 应有 IPv4 结果、AAAA 保持既有 IPv4 模式的空回答约定 |
| 域名 HTTPS | 经节点 DNS 通过后访问固定 Cloudflare 检查站点 | 验证完整请求与响应要求，失败不能直接认定节点认证错误 |

直连 DNS 失败后仍继续检查代理 DNS；代理 DNS 通过时继续 HTTPS，所以可以同时看到“直连 DNS 需要检查”和成功的代理结果。UI 使用服务冻结策略回执中的有限模式分类，不把保存设置误当成当前运行配置。

DNS 超时、格式异常和查询失败使用固定 stage／reason 分类；`direct-dns` 为新追加阶段，已有原因索引未重排。不会从任意错误文本提取域名、地址、凭据或推测根因。DNS 线协议回应本身不能显示其上游 DoH 的具体 HTTP／TLS 原因，本轮 HTTP 404 的证据来自私有核心日志，而非界面猜测。

每条 DNS 查询的绑定、发送与回答共用 6 秒总预算，关闭资源另有至多 1 秒等待预算。问题域名、事务 ID、查询类型、类别和回答格式均被校验。取消、会话变化、重连计数改变以及清理未确认不会报为成功；迟到 bind 仍尝试关闭，绝不发送迟到查询。未确认资源保留强引用，清理确认前不继续积累新的诊断 socket。

网络或会话变化后旧检查结果失效，等待网络的服务状态与 DNS 检查失败分开显示。物理网络 API 查询失败与没有可用网络不同，不能仅凭一个空查询结果判定设备已断网。诊断检查不修改 VPN 的连接状态；服务历史仍遵守单服务写入约定。

## 受控故障入口

入口仅完整核心调试包可用，要求上一会话已结束、固定测试类型和合法一次性 token，并在 30 秒入场窗口内启动。只创建本应用验证会话，服务再次核对请求类型与时效；不接受任意 URL、端口或完整核心配置。

测试从原设置产生独立内存策略：临时使用白名单 DNS 分流，保留节点与代理 DoH；正常或超时场景的直连地址使用公共阿里 DoH，HTTP 404 场景仅替换为该提供方的固定无效路径。策略不写入用户网络设置；会话停止使用既有正常清理流程。

| 固定类型 | 注入方式 | 会话上限 |
| --- | --- | --- |
| `baseline` | 正常直连 DoH，用于验证两条路径及网络恢复 | 5 分钟 |
| `http404` | 直连 DoH 使用固定不存在路径；TLS 继续正常验证 | 90 秒 |
| `timeout` | 真实固定 Xray 的直连解析器设 `timeoutMs: 1` 且禁用该解析器缓存 | 90 秒 |

极短超时用于主动触发核心截止时间，**不是对公共 DNS 自然响应速度的测量**。必须看到本次查询对应的真实截止时间日志，并确认未跨 DNS 路径；界面显示超时或配置中出现 `timeoutMs` 均不能单独证明注入成功。该注入不会修改 C++、Go 适配或上游 Xray／Hev 源码。

| 场景 | 当前结果与证据边界 |

| 从 0.22.0 升级 0.25.0 | API26／ARM64 手机安装和版本核对通过；升级前后 7 份用户文件按字节一致 |
| 正常分流基线 | 直连 DNS、代理 DNS 与 HTTPS 通过；测试使用本应用临时策略 |
| 直连 DoH HTTP 404 | 本次核心日志出现真实 HTTP 404；百度查询使用直连解析器，未观察到该查询改走代理解析器；代理 DNS 与 HTTPS 仍通过 |
| HTTP 404 结束 | 正常停止与清理核对通过；7 份用户文件与基线按字节一致 |
| 极短超时 | 本次核心日志出现 `context deadline exceeded`；百度查询使用直连解析器且没有代理 DNS 查询。首页显示直连失败，代理 DNS 与 HTTPS 仍通过 |

| 恢复网络后保持断开 | 用户恢复原网络后，约 60.84 秒、7 次独立检查均为同一已销毁会话，停止命令保留、旧服务进程不存在，未观察到新会话 |
| 日常模式复验 | 显式创建一次原有全局／代理 DNS 普通连接，有效策略与保存值一致且不带故障描述符，代理 DNS 与 HTTPS 检查通过，随后正常断开 |
| 最终收尾 | 本轮创建的 9 个会话均有清理回执；7 份用户文件与升级前基线按字节一致，原 schema 2 网络设置未被改写，最终 VPN 断开、服务进程不存在 |

404 检查将上一轮因调试输入未生效而未完成的实际故障场景补为本次手机上的限定实测，未修改[阶段三十历史记录](phase30-split-dns.md)。阶段三十的电脑性能数据属于不同设备与试验，不用于声称本次手机性能改善。

网络恢复初次试验达到 5 分钟保护时限并自动结束，未计作同会话恢复成功；重新建立短时会话后完成了等待网络、自动恢复及新查询核对。恢复过程中有 4 次保护拒绝，诊断历史确认均为网络切换后旧请求在保护前被拒绝；系统保护 API 失败和保护超时均为 0，不能将这部分拒绝写成“全程没有失败”。另一轮等待用户操作的短时会话也达到保护时限，已清理而未计作主动断开成功。最后主动停止检查采用已经断网时创建的等待会话，不能将其描述为已启动转发器在断网后被主动停止的真机复验；连接中断网与自动恢复已在另一会话独立验证。

日常模式的首次自动检查没有取得成功请求证据，已正常清理并保留记录。核对点击区域后，在开发工具页对原保存策略重新检查并成功；没有改动应用代码、节点或网络偏好来取得该结果。9 个会话的清理统计包括上述未计作成功的试运行，不等于 9 次完整联网成功。恢复后的不重连证据仅覆盖上述约一分钟的观察窗，没有长期稳定性或续航结论。

本轮只覆盖该手机、这一条节点及上述明确场景。API24 平板仍按此前要求暂停；没有在本轮操作或重新验收鸿蒙电脑。完整协议覆盖、所有手机系统、全天稳定性及更多 DNS 提供方故障需要独立验证。公开材料不包含节点资料、设备标识、原始核心日志、签名文件或调试 HAP。
