# 两种 HTTPS 耗时（0.16.0）

节点检测现在分别显示首次完整 HTTPS 请求耗时和第二次请求耗时。只有系统明确确认第二次复用了连接，才显示“复用延迟”；未复用或无法确认时，标为“再次 HTTPS”并注明连接情况。

此前同一鸿蒙手机、同一节点、同一 Cloudflare 地址的三组对照，首次与复用请求中位数分别为 2415 和 223 ms；gstatic 对照为 2560 和 232 ms。该实验说明，同一转发路径下首次请求与复用请求的连接状态、测量口径差异，就足以产生一个数量级的差距。它不是两客户端版本、配置全部一致的性能基准，也不证明首次连接没有优化空间。

## 使用方式

- 在断开状态进入节点页，点击“检测”，或依次检测当前筛选结果。
- “首次”指本轮第一个 HTTPS 请求，计入实际发生的域名解析、连接、TLS 及完整小响应耗时，不包含 VPN 启动时间。它不保证清空了系统 DNS 或所有底层连接状态，不应理解为绝对冷启动。
- 随后使用同一请求对象、同一地址进行第二次请求。两次分别计时，不取最小值代替首次耗时。
- 第二次超时或失败时，保留首次成功结果并显示单独提示。取消、网络改变、节点身份失效时，整次检测不能被迟到结果覆盖。
- “按首次耗时排序”只使用首次值，避免混排不同测量口径。旧记录显示“复用延迟 未检测（旧记录）”，重新检测后才获得第二个指标。

测试地址仍为 Cloudflare HTTPS trace，校验站点返回的固定格式；响应和地址信息不写入结果。TLS 正常校验，禁用重定向与响应缓存，每次请求上限 8 秒、两个请求合计上限 16 秒，临时 VPN 会话保留 30 秒上限。检测仅临时接管本应用流量，结束后清理，不改变当前选中节点。

## 实现与兼容

改动位于 ArkTS 探测、进程间结果协议、结果存储、VPN 服务接收和节点界面；C++、Hev 与 Xray 核心源码未修改。第二次复用状态使用 API 24 已提供的 `connectionExtraInfo.isReusedConnection`，缺失、类型不符或读取失败都归为未确认，不使用仅 API 26 提供的显式连接复用选项。

检测历史文件新写 schema 2，与节点库/节点备份的版本独立。严格读取旧 schema 1 并只在内存补充“旧单次测量”含义；首次读取不改写旧文件。下一次保存采用原子替换，保留节点指纹绑定、最多 500 条及格式/大小限制。主字段 `durationMs` 始终表示首次请求；新增字段记录测量版本、第二次状态、耗时、固定失败原因及连接复用情况。旧版应用不能读取新检测历史；开发回退时应同时恢复升级前的检测历史备份。

这些指标反映两个 HTTP 请求的耗时，不代表带宽、纯 TCP RTT，也不等同于 v2rayNG 核心直接拨号后两次请求取最小值的全部实现。[上游核心计时实现](https://github.com/2dust/AndroidLibXrayLite/blob/d0c6c4ae1b09c912070c8288bd0dbcc2e492ac29/libv2ray_utils.go#L66-L176)
