# 0.23.0：鸿蒙电脑后台与恢复验证

2026-09-23，在此前同一台 API26／ARM64 鸿蒙电脑上继续验证 0.23.0/code44。**本轮验证已完成**：约 30 分钟后台观察、返回后的联网与路由、系统睡眠／唤醒、断网自动恢复、主动断开后的不重连观察，以及三轮模式切换均取得对应证据。

本轮应用代码未修改；测试开始时重新记录当日节点、设置和服务状态基线。用户原有全局连接先通过 DNS／HTTPS 检查，再经正常断开确认清理，随后通过设置页保存白名单并建立新的测试会话。结束时恢复原全局设置、保留节点，并正常断开 VPN。

## 已完成：约 30 分钟后台资源观察

白名单连接在采样前通过应用内 DNS／HTTPS 检查，且实际路由记录确认百度 HTTPS 走 `direct`、Cloudflare 走 `nodeProxy`。随后最小化应用，确认它不在可见前台，开始独立的资源采样；没有在该窗口中执行模式切换或主动网络切换。

- 实际窗口 1,803.28 秒，每 30 秒一次，共 61 个有效样本；采样开始之间最大间隔 30.11 秒。
- 实时读取 `getconf CLK_TCK` 确认该设备为 100 ticks/s。以下 CPU 按“单个 CPU 核心为 100%”计算，不是整机百分比。
- 每个样本前后分别读回服务状态，共 122 份；同 runId、服务 PID、活动状态与心跳均通过核对。最大心跳年龄上界约 3.16 秒。
- 独立核对全部 122 份原始回执，核心快照均为活动中、版本 26.6.1；核心快照与状态写入时间最大差值 5 ms。Socket 保护失败和超时计数均为 0。
- 服务及 UI 的 PID／进程启动时间连续，未观察到恢复计数增加。UI 后台 CPU tick 未增加。

| 指标 | VPN 服务 | UI 进程 |
| --- | ---: | ---: |
| 时间加权平均 CPU | 4.75% | 0% |
| 30 秒区间 CPU p95 | 18.02% | 0% |
| 最高区间 CPU | 20.24% | 0% |
| RSS 起点 → 终点 | 163.48 → 150.98 MiB | 135.75 → 71.37 MiB |

| 文件句柄计数 | 系统拒绝读取，未测 | 系统拒绝读取，未测 |

期间有 CPU 波动，内存有上升和回落；这不是固定工作负载的空闲基准，未独立控制或测量其它应用的使用活动。一次窗口不能证明不存在内存泄漏，也不能推断续航。文件句柄缺失保留为未知，没有当作零。周期日志只作补充，未将“未读到错误日志”视为无错误的证明。

系统在窗口中自动熄屏／锁屏，采样结束后 `PowerManagerService` 为 `INACTIVE`。测试前后的 `SLEEP` 和 `HIBERNATE` 转换时间未增加，因此本段不是受控休眠／唤醒验证。

本地资源证据位于 `build/phase29-pc/soak-<本地会话>/`，包含 `samples.jsonl`、`summary.json`、脱敏的 `summary-safe.json` 和独立回执核对 `core-receipt-audit.json`。原始服务回执和设备身份仅保留在 Git 忽略的私有目录。

## 已完成：后台返回后的联网与分流

资源采样结束时，同一条白名单会话仍为 `active`。用户解锁并返回首页后，再次核对同一 runId／服务 PID 和新鲜心跳，没有重新建立连接。实际发起新的 DNS／HTTPS 检查并通过；随后通过浏览器发起带新参数的百度请求，核心日志增量确认走 `direct`，浏览器成功显示 robots.txt 内容，Cloudflare 检查仍走 `nodeProxy`。Socket 保护失败数保持 0。

采样前、后的路由回执分别保存，未用采样前的页面成功文字代替结束后的请求。当前已完成资源观察和后台返回的功能复验。

## 已完成：系统睡眠／唤醒后的功能复验

记录休眠前的新鲜活动会话、服务进程启动时间及 `PowerManagerService` 的电源状态转换时间后，用户通过系统电源菜单执行睡眠并唤醒。唤醒后观察到新的 `SLEEP` 状态转换记录，系统恢复 `AWAKE`；runId、服务 PID 和进程启动时间一致，活动回执及心跳新鲜，恢复计数仍为 0。

随后实际发起新的 DNS／HTTPS 检查并通过，再次验证百度请求走 `direct`、Cloudflare 走 `nodeProxy`。本次系统睡眠操作后的同会话功能恢复通过，没有通过手动断开、重新连接来掩盖恢复问题。

此设备拒绝执行临时的只读系统时钟探针，也未取得有效的内核启动标识；所传入的临时程序已删除。本次以系统电源状态记录、同一服务进程、新鲜状态及本轮新联网请求验证功能恢复，不据此宣称独立测得内核深度挂起时长。

## 已完成：完全断网后的自动恢复

用户关闭鸿蒙电脑网络后，同一会话进入 `waiting-network`，仍保持新鲜心跳，未结束 VPN。用户恢复原 Wi-Fi 后，同一 runId／服务 PID 自动回到 `active`，期间没有点击重新连接。网络属性变化先后触发两次核心恢复，恢复计数从 0 增至 2；随后再次读取保持稳定。

新的 DNS／HTTPS 检查通过，实际路由仍为百度 `direct`、Cloudflare `nodeProxy`。网络切换期间累计 13 次拨号在保护调用前因网络代次失效而被拒绝，诊断分类为 `protect-stale-before`；`protect-stale-after`、`protect-api-failed` 及保护超时均为 0。这与 30 分钟资源采样期间的零失败统计属于不同阶段，不能混写为整轮始终零拒绝。网络恢复后的新请求成功，拒绝计数没有继续增加。

## 已完成：断网时主动停止，恢复网络后保持断开

用户再次关闭物理网络后，先核对同一会话处于新鲜的 `waiting-network`，再确认首页显示“等待网络”且按钮为“断开”，通过正常 UI 断开。该会话最终写入 `destroyed`、`cleanupConfirmed=true`，独立两次核对回执稳定及服务进程不存在。

用户恢复物理网络后，没有点击连接。连续约 61 秒、7 次检查均保留同一终止回执、停止命令和服务进程不存在，没有观察到替代会话。期间通过浏览器发起带新查询参数的普通网页请求，地址中确认了新参数，页面返回 robots.txt 内容，证明系统网络已经可用。此结果限于该观察窗口；不把后面测试员主动启动的连接误算为自动重连。

## 已完成：模式切换与收尾

随后通过正常 UI 完成三轮独立连接，各轮均为保存模式 → 连接 → 新 DNS／HTTPS 检查 → 路由检查 → 正常断开：

| 模式 | 百度请求路由 | Cloudflare 检查 | 断开清理 |
| --- | --- | --- | --- |
| 全局 | `nodeProxy` | 通过、`nodeProxy` | 通过 |
| 白名单 | `direct` | 通过、`nodeProxy` | 通过 |
| 全局 | `nodeProxy` | 通过、`nodeProxy` | 通过 |

连同最初的原有全局连接及长时间白名单会话，5 个不同会话均核对了同 runId／服务 PID 的清理回执、独立重复读回，以及两次进程不存在。最后停留首页并显示“未连接”。

收尾重新读取全部 12 个状态文件并独立复读，结果稳定。节点库、节点配置、网络策略、延迟记录、恢复记录、外观及延迟请求／证明共 8 个文件与当日初始基线逐字节一致（原本缺失的仍缺失）；连接日志及控制状态保留本轮真实操作。原全局模式和窗口几何均恢复，应用代码与当前提交一致。最终完成记录保存在本地 `build/phase29-pc/completion.json`，个人节点、设备标识与原始日志不发布。

这些结果支持当前一台 API26 电脑、当前节点与网络下的上述场景，不外推为所有设备、节点协议、全天稳定性、句柄无泄漏、内核深度休眠或续航验收。API24 平板测试仍按此前要求暂停。
